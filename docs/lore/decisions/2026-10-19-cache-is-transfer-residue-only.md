# 「本地缓存」只等于「传输中断的残留」，成功传输的中转文件按协议即删、不累积
- 日期：2026-10-19
- 状态：已采纳（已向用户说明，待确认；若用户坚持全量手动累积，改动仅为删除两处 delete 调用）
- 关联约束：INV-005
- 关联坑点：pitfalls/2026-10-19-cache-button-dead-by-display-rounding.md

## 背景

用户反馈缓存恒为 0 MB、怀疑存在自动清理，要求「改为让用户手动清理」。排查结论：
启动时自动清理早已移除（93960da）；剩下的自动删除只有**传输协议自身的收尾**——
接收临时分块落盘成功后删除（`FileReceiver.completeReceive`）、分享中转副本上传
终结后删除（`ShareReceiveActivity`）。于是问题变成：要不要把这两处也改成「不删，
等用户手动清」，让缓存行正常使用时也能涨？

## 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A（最终采用）：保持协议收尾即删，缓存行只管「中断残留」；另修显示/判定 bug 让残留可见可清 | 不产生隐藏占用；「缓存」语义诚实（异常残留才需要清） | 正常使用下缓存行长期显示 0 KB，按钮多数时间无事可做 |
| B：成功/失败的中转文件都不删，全部等手动清理 | 缓存行随时有内容可清，按钮「有用」 | 每收/发一个文件都在私有目录留下等量副本——1 GB 视频即 1 GB 隐藏占用，用户感知不到，违背「缓存」语义；与旧版 §3.9 设计（临时文件只是中转）冲突 |

## 结论与理由

选 A。「中转文件完成后删除」是传输协议的一部分，不是「缓存清理」；把它算进缓存
等于把功能正常的代价（双倍存储）转嫁成用户的家务。缓存行的定位保持为
「异常残留的清道夫」，配合 INV-005 修复后，有残留时一定能看到、能清掉。

**未来应重新评估的条件**：用户确认希望保留传输副本另作他用（如「最近发送」列表）——
那应该做成有 UI 展示的正式功能（可见、可单删），而不是堆在缓存里。
